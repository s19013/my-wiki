# 3. バックアップ

## 旧サーバーのバックアップは、なぜ 3 年半ずっと空だったのか

cron には、毎日次のスクリプトが登録されていた。

```sh
mysqldump --single-transaction -u $DBUSER -p$DBPASSWORD $DBNAME | gzip > $exportDirectryPath/$DBNAME-$date.dump.gz
```

ログインしてこのスクリプトを手で実行すると、ちゃんと動く。それでも cron から実行すると、毎回 20 バイトの空ファイルができていた。

### 原因 1: cron の PATH は最小限

| 実行のしかた | PATH | mysqldump |
|---|---|---|
| SSH でログインして実行 | `.bashrc` などで `/opt/bitnami/mariadb/bin` が追加されている | 見つかる |
| cron から実行 | `/usr/bin:/bin` だけ | **見つからない** |

Bitnami は MariaDB を `/opt/bitnami/` の下に入れているので、cron の PATH からは見えなかった。

> **教訓:** 「手で実行すると動くのに cron だと動かない」ときは、まず PATH を疑う。cron からは、コマンドをフルパスで呼ぶか、PATH を明示する。

### 原因 2: パイプは、前のコマンドの失敗を無視する

```sh
mysqldump ... | gzip > file.gz
```

mysqldump は「コマンドが見つからない」で失敗する。それでも gzip は、空の入力を受け取って、空の gzip ファイル（20 バイト）を作って **正常終了** する。シェルはパイプの最後のコマンドの結果しか見ないので、全体としては「成功」になる。

### 原因 3: 失敗に気づく仕組みが無かった

cron は、コマンドの出力をメールで送ろうとする。しかしサーバーにメールの仕組みが無かったので、`No MTA installed, discarding output` として捨てられていた。

> **教訓:** バックアップは、「ファイルができている」だけでは何の保証にもならない。中身を確かめ、実際に復元できることを試す。

## 新しい仕組み

```
cron（毎日 02:22 UTC）
  └─ deploy/backup.sh
       ├─ db コンテナの中で mariadb-dump → gzip → 一時ファイル
       ├─ 中身を確かめる（だめなら失敗させ、ファイルも残さない）
       ├─ /var/backups/my-wiki/ に保存（14 日分）
       └─ S3 に送る（30 日経ったら自動で削除）
```

### set -euo pipefail

[backup.sh](../backup.sh) の先頭にある。

| オプション | 意味 |
|---|---|
| `-e` | どれかのコマンドが失敗したら、そこで止まる |
| `-u` | 未定義の変数を使ったら止まる（打ち間違いを防ぐ） |
| `-o pipefail` | パイプの途中のコマンドが失敗したら、パイプ全体を失敗にする（原因 2 の対策） |

### 中身の確認

```sh
gzip -t "$tmp"                                         # gzip として壊れていないか
zcat "$tmp" | tail -n 1 | grep -q '^-- Dump completed'  # 最後まで書き出せたか
zgrep -q '^INSERT INTO `articles`' "$tmp"               # 本当にデータが入っているか
```

ダンプは、まず一時ファイル（`.名前.tmp`）に書き出す。確認がすべて通ってから、本来の名前に `mv` する。これで、「中途半端なファイルが正式なバックアップに見える」ことがなくなる。
失敗したときは `trap` で一時ファイルを消す。

空のダンプを実際にわざと作って、きちんと失敗することも確かめてある。

### cron で PATH を明示する

[setup-server.sh](../setup-server.sh) が作る `/etc/cron.d/my-wiki`:

```
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
22 2 * * * ubuntu /srv/my-wiki/deploy/backup.sh
24 2 2 * * ubuntu /srv/my-wiki/deploy/cleanup.sh
```

`/etc/cron.d/` に置くファイルは、`crontab -e` と違って **実行ユーザーの欄**（ここでは `ubuntu`）がある。

結果は syslog に `my-wiki-backup` という名前で記録される（`grep my-wiki /var/log/syslog`）。

## S3 に送る理由

サーバー上のバックアップは、サーバーのディスクが壊れたり、インスタンスを消してしまったりしたら一緒に消える。だから別の場所にも置く。
Lightsail の自動スナップショットでもよかったが、費用を抑えるため S3 にした。ダンプは 3〜4MB で、30 日分を置いても月に約 1 円。

### 最小権限（書き込み専用のキー）

サーバーに置く AWS のキーは、**このバケットに書き込むことしかできない** 専用の IAM ユーザーのもの。

```json
{
  "Effect": "Allow",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::my-wiki-backup-394572168692/my-wiki/*"
}
```

サーバーが乗っ取られてこのキーが盗まれても、できることは「ファイルを書き込む」ことだけ。過去のバックアップを読むことも、消すことも、他の AWS リソースを触ることもできない。実際に試して、すべて拒否されることを確認した。

| 操作 | 結果 |
|---|---|
| ファイルを書き込む | ✅ できる |
| 一覧を見る / 読み出す / 削除する | ❌ AccessDenied |
| EC2 などほかのサービス | ❌ UnauthorizedOperation |

その代わり、S3 からバックアップを取り出すときは、手元の PC から（自分の権限で）行う。

### バケットの設定

[create-backup-bucket.sh](../create-backup-bucket.sh) が次を設定する。

- パブリックアクセスをすべてブロック
- ライフサイクルルール: 30 日経ったファイルを自動で削除（古いファイルの片付けをサーバー側でやらなくて済む。サーバーのキーには削除の権限が無いので、そもそもできない）

S3 へのアップロードには `amazon/aws-cli` の Docker イメージを使った。サーバーに aws cli を入れなくて済む。

## 復元を試す

「バックアップが取れた」と言えるのは、**復元できることを確かめてから**。ローカルで次の往復を試した。

1. `backup.sh` でダンプを取る
2. わざと記事を 100 件消す（2577 件 → 2477 件）
3. `restore.sh` で戻す
4. 件数が元どおり（2577 件）になり、紐づくタグの件数も一致することを確かめる

ダンプには、テーブルごとに `DROP TABLE IF EXISTS` が入っている。そのため、復元すると DB はダンプの時点の状態にそっくり置き換わる。

## 掃除処理（cleanup.sh）

論理削除（`deleted_at` に日時が入っているだけで、データは残っている状態）から半年たったデータを、完全に削除する。旧サーバーにもあった処理だが、同じく PATH の問題で一度も動いていなかった。

新サーバーで最初に動いたとき、溜まっていた記事 416 件・ブックマーク 40 件・タグ 19 件が消える（了承済み）。消える前のデータは、移行時のダンプに残っている。
